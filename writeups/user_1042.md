## Executive Summary

`User 1042` demonstrates a classic **Insecure Direct Object Reference (IDOR)** vulnerability—ranked as the #1 threat in the OWASP API Security Top 10 (Broken Object Level Authorization). The web portal allows authenticated users to inspect officer profiles by querying an `id` parameter. To obfuscate database keys, the developer hashed sequential integers using MD5. While the high-privilege "President" profile card is visually locked in the web interface and lacks an HTML link, the backend endpoint performs zero authorization checks. By calculating the MD5 hash of the zero-index user (`MD5("0")`), we query the endpoint directly and extract the flag.

---

## Fundamental Concepts for Beginners

### 1. What is an IDOR (BOLA)?
An **Insecure Direct Object Reference** occurs when an application exposes a reference to an internal database object (such as a database row ID, filename, or account number) in a URL or API parameter, and **fails to verify** whether the currently authenticated user is authorized to access that object.

```
+------------------+                                      +--------------------+
| Attacker Browser |                                      | Web Server Backend |
+------------------+                                      +--------------------+
         |                                                           |
         |  GET /profile?id=md5(1) [Vice President]                 |
         |---------------------------------------------------------->|
         |  200 OK: Displays Vice President Profile                  |
         |<----------------------------------------------------------|
         |                                                           |
         |  GET /profile?id=md5(0) [President - High Privilege]      |
         |---------------------------------------------------------->|
         |                                                           |
         |  MISSING CHECK: Does the user have admin permission?      |
         |  NO CHECK! Backend queries DB directly:                  |
         |  SELECT * FROM profiles WHERE id = '0'                    |
         |                                                           |
         |  200 OK: Dumps President Profile & Flag!                  |
         |<----------------------------------------------------------|
```

### 2. Obfuscation is NOT Authorization
Developers often attempt to stop IDOR vulnerabilities by replacing sequential numbers (`?id=1`, `?id=2`) with hashes (`?id=c4ca42...`). 
However:
- **Hashing $\ne$ Encryption:** Hashes cannot be decrypted with a secret key, but predictable inputs can be instantly reversed using precomputed lookup tables (rainbow tables).
- **Hashing $\ne$ Access Control:** If anyone can calculate the hash of ID `0`, and the server blindly accepts it without checking privileges, the system is entirely unauthenticated.

The challenge hint advises:
> *"But every society has someone at the top. You don't see them here... Doesn't mean they're not reachable."*

In relational databases and software engineering, administrative or foundational entries are routinely assigned index **`0`** (e.g., `UID 0` for `root`).

We calculate the MD5 hash of string `"0"`:


## Remediation & Defensive Architecture

To secure applications against Broken Object Level Authorization:

1. **Enforce Server-Side Authorization Checks:**
   Never assume that a user is allowed to view an object just because they submitted its ID:
   ```python
   @app.route('/profile')
   @login_required
   def profile():
       requested_id = request.args.get('id')
       profile = Profile.query.filter_by(id=requested_id).first_or_404()
       
       # CRITICAL CHECK:
       if not current_user.can_view(profile):
           abort(403) # Forbidden!
       return render_template('profile.html', profile=profile)
   ```
2. **Use Cryptographically Secure GUIDs (UUIDv4):**
   Do not use sequential integers or simple hashes of integers for public references. UUIDv4 provides 122 bits of pure entropy, eliminating ID enumeration attacks.
3. **Never Rely on Client-Side Hiding:**
   Disabling a button or omitting a link in HTML does not prevent attackers from sending raw HTTP requests. Security must always be enforced on the backend.
